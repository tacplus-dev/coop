- **A security report from the build pipeline, and the README sections that point to it** (2026-11-06, nightly scan): coop's only workflow is `.github/workflows/planning-files.yml`. No pipeline runs `govulncheck` or scans the image, and the README has no "Security checks" or "Trace propagation" section, though the nightly scan is told to read both. Each night the scan runs `govulncheck ./...` itself, so a vulnerability shows up only once a day and not on the change that brings it in. Proposed: a `security` workflow that runs `govulncheck` (and an image scan once #2 publishes one) on push and PR and keeps its report as an artifact, plus a README "Security checks" section naming it and a "Trace propagation" section summarising `decisions/trace-propagation-2026-11-03.md` as coop applies it (STATE.md has it today). Related: tacplus-dev/fleet-seatrials#38 (its `security.yml`), the platform roadmap's nightly scans (tacplus-dev/looper#49). Updated 2026-11-12 (nightly scan): the looper's build now runs the deterministic checks (looper-scan: govulncheck, osv-scanner, gosec, gitleaks, semgrep, trivy and others) and keeps `security/summary.md` and `findings.json` per run. First, of its 466 findings, 465 are in the generated, uncommitted `tacplus/` tree (all 239 HIGH gosec failures and all 3 gitleaks "secrets", which are test fixtures in `tacplus/chassis/collection/page_behavior_test.go` and `tacplus/chassis/logger/logger_security_test.go`). - **The security checks cover the launcher the release image ships** (2026-11-17, nightly scan, #14): `release.yml` builds tacplus-dev/launcher from source at `LAUNCHER_COMMIT` and copies it into the image as PID 1, but the build's checks (looper-scan) scan only coop's go.mod, sources and Dockerfile, so the pinned c54ae30, which still has launcher#7's G402 (the probe skips certificate verification), showed up in no report. Proposed: looper-scan (or a gate) checks the pinned launcher commit, at least that it is at or after the launcher's latest release, or scans its go.mod and source the way coop's own are. A `HEALTH_PORT` that the pinned launcher's probe cannot pass would be worth checking too. That check is the same in kernel, eventbus and stratum (launcher's STATE.md: eventbus and stratum set 8443 with no `HEALTH_CA`). Related: tacplus-dev/looper#49, tacplus-dev/kernel#22. Updated 2026-11-17 (#14): the image now takes launcher v0.1.0 from its release, pinned by sha256 in the Dockerfile, and probes 8444; `ci/release_test.sh` checks the pin is at or after v0.1.0 and the port is plaintext, but not that the pinned version is the launcher's latest, nor its binaries' vulnerabilities (looper-scan could check the Dockerfile's `LAUNCHER_VERSION` against the launcher's releases). llmproxy and gateway still COPY a launcher from beside their Dockerfile with `HEALTH_PORT=8443`, as eventbus and stratum do.
- **Drop release.yml's launcher source build** (2026-11-17, #14): since #14 the Dockerfile takes the launcher from its release, pinned by sha256, so `release.yml`'s `LAUNCHER_COMMIT` (still c54ae30, before launcher#7), its tacplus-dev/launcher checkout, `setup-go` and "launcher, each platform" steps build a binary nothing uses, and `ci/release-image.sh`'s LAUNCHERS argument copies it into a context the Dockerfile ignores. A looper cannot change `.github/workflows/` (its App has no `workflows` permission), so a person removes them: the four steps and the env line, `.release/launcher` from the release-image.sh call, and the LAUNCHERS argument from `ci/release-image.sh` and `ci/release_test.sh` (the patch is on #14).
- **Pigeon egress and isolation in a tenant namespace** (2026-11-26, #17): since #17 a shared coop runs each tenant's pigeons in that tenant's namespace (`tac-<deployment>-<tid>`), whose egress (deploymentproxy's) stops at the namespace, DNS and `tac-<deployment>`. A pigeon reaches external domains (its kind's `domain_ceiling`), so unless it goes out through a proxy in `tac-<deployment>` (slice 3, "egress through a proxy") it is cut off there; and it now shares the namespace, and its intra-namespace egress, with the tenant's own services, where the old pigeons namespace held nothing else. coop renders no NetworkPolicy: the operator or deploymentproxy would render one for pods labelled `coop.tacplus.dev/run` (on every pigeon pod). Pigeons also count against the tenant's quota now; a Job the quota refuses fails its start and the run ends FAILED. Not observed on a live fleet yet (seatrials moves with tacplus-dev/fleet-seatrials#4 and tacplus-dev/operator#47).
